# SQL connections

The [Query data](/data-query) page and the Data tabs run queries in the app. A **SQL connection** lets the tools you already use do the same: Power BI, Excel, Tableau, DBeaver, Metabase, `psql`, and anything with a PostgreSQL JDBC or ODBC driver. Classifyre answers as a PostgreSQL database: the workspace is the database, each source schema is a schema, each table you may query is a table.

- **Nothing is reachable until it is opened.** A source or table is reachable through SQL connections only after its owner, a steward or an admin opens it on its **Governance** tab (opening a source opens all its tables). Opening gives nobody access: people still need the right to query it.
- **It names what it is for.** Like *Give access*, a connection is for a whole source or for single tables — chosen from what is open and what you may query. Only admins and people who answer for data (owners, stewards, custodians) may make or give one for everything open.
- **It is yours.** A connection belongs to one person and reads exactly what that person may query right now — their roles, their Data reader grants, the tables they own. It never gives access of its own: when a grant is removed, the connection stops reading that table at once.
- **Masks apply.** Columns governance masks or hides for its person are masked or missing here too, and a masked column's description says so (see [Masked and hidden columns](/data-query#masked-and-hidden-columns)).
- **Row filters apply.** A table that shows its readers only some rows shows the connection's person only theirs (see [Filtered rows](/data-query#filtered-rows)).
- **Everything is recorded.** Every table read through a connection is in the table's **Activity** and **Usage**, with the person and the connection's name.
- **It can be taken back.** Its person or an admin can revoke it; a table's owner can close their table to one connection; it expires.
- **No password is stored.** Only a SCRAM-SHA-256 verifier is kept. The password is shown once, to its person only, and never crosses the network.

## Make a connection

<Steps>
### Open Settings → SQL connections

Choose **New connection**, name it after the tool (`Power BI`, `DBeaver`), choose the sources or tables it is for, and pick when it expires. From a table's or source's **Data** tab, **Connect a tool → New connection for …** starts with that table or source already chosen.

### Copy the password

It is shown once. Lost it? **New password** replaces it; tools signed in with the old one stop at their next sign-in.

### Connect the tool

The dialog shows the host, port, database and user, and the same as a `psql` line, a JDBC URL, an ODBC string and a Power BI connection string. **Connect a tool** next to the SQL editor shows them again at any time.
</Steps>

You need the right to query tables to make a connection: the **Data reader** role (on the workspace, a source or a table), a workspace admin role, or tables you own.

### Given by an owner or admin

A table's or source's owner or steward can **give a connection** for it to someone on its **Governance** tab, and an admin can give one for anything. The person is notified and reveals the password themselves — the one who gave it never sees it. The connection reads only what it was given for, and only if the person may read it: an owner who wants someone to read their table also grants them access (or approves their request).

## Connect your tool

The connection dialog adapts to your installation's TLS setting (see [TLS and certificates](#tls-and-certificates)):

- **TLS with a private or chart-managed CA** *(Helm chart default)*: connections use TLS 1.3 with `sslmode=verify-full`. Click **Download the certificate authority** (`classifyre-sql-ca.crt`) in the dialog and point your tool at it.
- **TLS with a publicly trusted certificate** *(Let's Encrypt / `certManager` / `existingSecret` without `ca.crt`)*: connections use TLS 1.3 with `sslmode=verify-full`; your operating system or driver already trusts the CA, so no download is shown or needed.
- **TLS disabled** *(all-in-one Docker default, or Helm `sqlGateway.tls.enabled: false`)*: no certificate is used or downloaded; tools connect with `sslmode=disable`.

Copy the ready-made strings straight from the dialog — they already match your deployment's SSL mode and whether a CA file is needed.

### Naming tables

A table you see on the Query data page as `source.schema.table` is the PostgreSQL table `"source.schema".table` — the quotes are needed because of the dot. Tools quote names for you; when writing SQL by hand, set the search path once:

```sql
SET search_path = "lake_finance.ledger";
SELECT * FROM invoices WHERE amount > 1000;
```

Without quotes, PostgreSQL reads `source.schema.table` as *database.schema.table* and refuses it; write `"source.schema".table`, or `"lakehouse-lab"."source.schema".table` with the workspace as the database.

### Tools that pool connections

Metabase, Tableau Server and application servers keep several connections open to the same database. A SQL connection allows **4 sessions at a time** (`sqlGateway.maxSessionsPerConnection`); a pool larger than that cannot open its extra connections, and some tools then give up on all of them. Set the tool's pool to 4 or fewer (Metabase: `MB_JDBC_DATA_WAREHOUSE_MAX_CONNECTION_POOL_SIZE=4`). Connections a pool opens at the same moment sign in one after the other (each waits up to 10 s for the one before it), so a pool of 4 opening at once is fine.

Everyone using such a tool reads through its one SQL connection, with **its** person's access: give a shared BI tool a connection of a person (or a scope) whose access every user of that tool may have. Values the tool stores for its filters come through that connection too, masked as that person sees them.

## What happens to a query

Catalog queries — the schemas, tables and columns tools read to show you what is there — are answered at once from a PostgreSQL catalog made for your session. A query that reads your tables runs exactly like one from the Query data page: the same SQL gate (one read-only statement, only the tables you may read), the same time limit, recorded per table.

- **Rows.** A result has at most the workspace's row limit (Settings → General, 10,000 by default), or its export limit if you may export (`data.export`). More is refused with an error, never cut silently: add a filter or a `LIMIT`. A result your tool reads page by page (a JDBC fetch size, a Metabase download) arrives in full.
- **Read only.** `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `CREATE`, `COPY`, `DO` blocks and the like are refused before they run, with PostgreSQL's read-only error (`25006`).
- **Cursors.** `DECLARE … CURSOR` and `FETCH` over your tables work as in PostgreSQL: a cursor ends with its transaction unless it is declared `WITH HOLD`, and one connection holds at most eight at once. Scrollable cursors, reading backward and cursors declared through a prepared statement are refused with a clear error, never answered with no rows.
- **Not served.** `PREPARE`/`EXECUTE`, `CREATE TABLE … AS` and `EXPLAIN ANALYZE` over your tables are refused; tools that prepare statements through the protocol (JDBC, psqlODBC, Npgsql) are not affected.
- **Busy.** When the gateway is short of memory it refuses new connections as busy rather than dropping the open ones; tools retry.
- **Cancel** in your tool stops the query.
- **Mixing.** One statement reads either your tables or the catalog (`pg_catalog`, `information_schema`), not both.

### Speed

A query runs in the warm query worker and usually answers in about a second, like one from the Query data page. Queries that read an [ODBC](/sources/odbc/) or [custom](/sources/custom-connectors/) source, and queries the worker has no room for, start a short-lived Job instead, which takes a few seconds before the query itself runs. Tools that import data (Power BI import mode, Excel, extracts in Tableau) work well with either; dashboards that send many queries at once are fastest on native sources.

## Opening a source or table

On a table's or source's **Governance** tab, the **Access** step starts with **Open to SQL connections**. Its owner, a steward or an admin switches it on; a table is open when it or its source is. **Settings → SQL connections** lists everything open, by whom and since when. Closing it again stops every connection from reaching it at once.

## Governance and activity

On a table's or source's **Governance** tab, **Access** lists the SQL connections that read it in the last 90 days, how often and when, whose they are, and those its scope names or that are closed on it. Its owner and stewards can:

- **give a connection** for it to a person;
- **close it here** for one connection — the rest of that connection keeps working, and its person is told;
- open it again.

The table's **Activity** shows each read with the connection's name (*via SQL connection Power BI*), and its **Usage** counts the people reading it, however they read. Creating, giving, revealing, revoking and closing connections, sign-ins (at most once an hour per connection) and refused sign-ins are on the workspace's activity too.

## Who may do what

| | Its person | Owner or steward of a table/source | Admin (`data.connection.manage`) |
| --- | --- | --- | --- |
| Open a table or source to SQL connections | | for what they govern | ✓ |
| Make one for themselves | ✓ for open sources/tables they may query (`data.connect`, a Data reader grant, or tables they own) | ✓, also for everything | ✓, also for everything |
| See its password | ✓, once per password | never | never |
| Give one to someone | | for open sources and tables they govern | for anything open; for everything only to an admin, owner, steward or custodian |
| Close a table or source to one | | for what they govern | ✓ |
| Revoke | ✓ | | ✓ |
| See them | their own | those that concern their table | all |

The **Data reader** role includes `data.connect`; a Data reader grant on one table lets its holders connect a tool to that table.

## Making the endpoint reachable

Administrators: the endpoint is the **SQL gateway**, a separate service of the same image. It is **on by default** (Helm `sqlGateway.enabled: true`; the all-in-one image runs it too), but until you tell it where people reach it, the app shows a warning instead of connection details:

> **SQL connections are not configured yet.** The SQL gateway is running, but it has no public address.

You see it on **Connect a tool** (which also carries a warning icon), on **Settings → SQL connections** and on a table's or source's **Governance** tab, each with a link to this section. Two things clear it:

1. **A public host**: the name your tools connect to (`sqlGateway.publicHost`, or `SQL_GATEWAY_PUBLIC_HOST` in Docker). It is shown in the app next to every connection (and put in the gateway's certificate when TLS is enabled). `sqlGateway.publicPort` is the port as your tools see it (the default 5432; a NodePort's or an entrypoint's port otherwise).
2. **A TCP path to the gateway's port.** The gateway speaks the PostgreSQL protocol (with optional TLS 1.3 terminated at the gateway), so a plain HTTP Ingress or an HTTPRoute **cannot** carry it. Pick the row that matches your cluster:

| Where it runs | Use | `publicHost` | `publicPort` |
| --- | --- | --- | --- |
| A cloud cluster (EKS, GKE, AKS) or MetalLB | a `LoadBalancer` Service | the DNS name you point at the load balancer | the Service port (`sqlGateway.port`, 5432) |
| One node, no load balancer (k3s, a VPS) | a `NodePort` Service | the node's DNS name or IP | the node port (`sqlGateway.service.nodePort`, 30000–32767) |
| Traefik v3 | an `IngressRouteTCP` | the DNS name of Traefik's address | the Traefik entrypoint's port |
| ingress-nginx | its `tcp-services` ConfigMap | the DNS name of the controller's address | the port you list there |
| Another TCP proxy (HAProxy, Envoy, a Gateway API `TCPRoute` or `TLSRoute`) | forward TCP, **passing TLS through** | the proxy's DNS name | the proxy's port |
| A laptop cluster (k3d, kind, minikube) | `kubectl port-forward` | `localhost` | the local port you forward |
| Docker (all-in-one) | `-p 5433:5433` | the host of `CLASSIFYRE_URL` (default `localhost`) | `5433` |

<Tabs items={["LoadBalancer / NodePort", "Traefik", "ingress-nginx", "Other TCP proxy", "Local cluster", "Docker"]}>
<Tabs.Tab>
Without a TCP-capable proxy, give the gateway its own address:

```yaml
sqlGateway:
  publicHost: sql.example.com
  publicPort: 5432
  service:
    type: LoadBalancer           # or NodePort (then publicPort is the node port)
    # nodePort: 30543            # NodePort: a fixed port in 30000-32767
    loadBalancerSourceRanges: [203.0.113.0/24]
    externalTrafficPolicy: Local # keeps client addresses for allowedCidrs
  allowedCidrs: [203.0.113.0/24]
```

For a `NodePort`, set `publicPort` to the node port and open that port in the node's firewall. By default (`sqlGateway.tls.enabled: true`), the chart makes a certificate authority and a certificate for `publicHost` and keeps them across upgrades; people download the CA from the app. You can also bring your own certificate (`sqlGateway.tls.existingSecret`), use cert-manager (`sqlGateway.tls.certManager`), or opt out of TLS (`sqlGateway.tls.enabled: false`). See [TLS and certificates](#tls-and-certificates).
</Tabs.Tab>
<Tabs.Tab>
Traefik v3 routes PostgreSQL with an `IngressRouteTCP`. Give it an entrypoint (`--entryPoints.postgres.address=:5432`) and:

```yaml
sqlGateway:
  publicHost: sql.example.com
  publicPort: 5432     # the entrypoint's port
  traefik:
    enabled: true
    entryPoints: [postgres]
    tls: none          # raw TCP, TLS end to end with the gateway: every client works
  proxyProtocol: true  # optional: real client addresses for lockouts and allowedCidrs
```

`tls: passthrough` routes by host name (SNI) on a shared entrypoint: Traefik answers PostgreSQL's SSL request and passes the encrypted stream to the gateway, which still holds the certificate. It requires `sqlGateway.tls.enabled: true` and `publicHost` (the chart refuses to render otherwise). TLS always ends at the gateway (TLS 1.3); Traefik never sees the plain protocol. With `sqlGateway.tls.enabled: false`, use `tls: none`.

With `proxyProtocol: true`, also set `trustedProxies` to Traefik's pod or node networks: the gateway then accepts a PROXY header only from there, so nobody reaching the pod directly can claim another client address.
</Tabs.Tab>
<Tabs.Tab>

- To keep real client addresses for lockouts and `allowedCidrs`, have the proxy send the PROXY protocol (v1 or v2) and set `sqlGateway.proxyProtocol: true` together with `trustedProxies` (the proxy's networks). Never turn `proxyProtocol` on when some connections arrive without it.

### TLS and certificates

TLS on the SQL gateway is controlled by `sqlGateway.tls.enabled` in Helm and `SQL_GATEWAY_TLS_ENABLED` in the environment:

- **Default in general & in Helm**: **enabled** (`true`). Every connection negotiates TLS 1.3 and verifies the server certificate (`sslmode=verify-full`).
- **Default in the Docker all-in-one image**: **disabled** (`false`). No certificate is generated or mounted, and BI tools / ODBC connect directly without downloading a CA (`sslmode=disable`).

How the three certificate modes work:

| Mode | Configuration | Certificate | App shows CA download? | Client SSL mode |
| --- | --- | --- | --- | --- |
| **Chart-managed CA** *(Helm default)* | `sqlGateway.tls.enabled: true` (no `existingSecret`, `certManager.enabled: false`) | Chart generates a private CA + leaf cert for `publicHost` once and keeps them in Secret `<release>-sql-tls` | Yes (`classifyre-sql-ca.crt`) | `verify-full` + `sslrootcert` |
| **Public or enterprise CA** | `sqlGateway.tls.enabled: true` + `existingSecret` or `certManager.enabled: true` | Your `kubernetes.io/tls` Secret (`tls.crt`, `tls.key`, optional `ca.crt`) or cert-manager Certificate | Only if `ca.crt` is present in the Secret | `verify-full` (no CA file needed for public CAs) |
| **No TLS / no certificate** *(Docker default, opt-out in Helm)* | Helm: `sqlGateway.tls.enabled: false`<br/>Docker / env: `SQL_GATEWAY_TLS_ENABLED=false` | None generated, none mounted | No | `disable` |

#### How the certificate download works

When TLS is enabled, the gateway loads `tls.crt` and `tls.key` (`SQL_GATEWAY_TLS_CERT_FILE`, `SQL_GATEWAY_TLS_KEY_FILE`) and requires TLS 1.3 (both PostgreSQL `SSLRequest` and direct TLS `sslnegotiation=direct` are supported). Separately, the API reads the public CA certificate from `SQL_GATEWAY_TLS_CA_FILE` (only `ca.crt` is mounted into the API pod — never the private key) and returns it from the connection endpoint so the UI shows **Download the certificate authority** (`classifyre-sql-ca.crt`) and adds `sslrootcert=classifyre-sql-ca.crt` to the copy-paste connection strings.

- **If you want TLS without users downloading a CA**: use a certificate signed by a public CA (such as Let's Encrypt via `sqlGateway.tls.certManager`) or your organization's already-trusted enterprise CA in `sqlGateway.tls.existingSecret`, and omit `ca.crt` from the Secret. The app then hides the CA download button while keeping `sslmode=verify-full`.
- **If you want to opt out of TLS and certificates completely**: set `sqlGateway.tls.enabled: false` in Helm (or `SQL_GATEWAY_TLS_ENABLED=false` in the environment). No TLS Secret or Certificate resource is created, no certificate files are mounted, the gateway answers PostgreSQL's `SSLRequest` with `N` and accepts plain TCP connections, and the app switches every connection string to `sslmode=disable` with no CA download.

```yaml
# Opt out of SQL gateway TLS in Helm (trusted private network / VPN only)
sqlGateway:
  publicHost: sql.internal.example
  tls:
    enabled: false
```

```yaml
# Use a publicly trusted Let's Encrypt certificate via cert-manager (no CA download needed)
sqlGateway:
  publicHost: sql.example.com
  tls:
    enabled: true
    certManager:
      enabled: true
      issuerRef:
        name: letsencrypt-prod
        kind: ClusterIssuer
```

<Callout type="warning">
  With TLS disabled, passwords still never cross the network in plain text (every sign-in uses SCRAM-SHA-256), and all masking, row filters and audit logs remain enforced. However, SQL queries and result rows travel unencrypted over TCP. Keep `sqlGateway.tls.enabled: true` whenever traffic crosses an untrusted network; disable it only for local use, a trusted private network, or behind a VPN/tunnel.
</Callout>

#### Rotating or regenerating the chart-managed certificate

The chart-managed Secret (`<release>-sql-tls`) carries `helm.sh/resource-policy: keep` and is looked up on upgrades so clients that downloaded `classifyre-sql-ca.crt` keep working. If you change `sqlGateway.publicHost` or `sqlGateway.tls.extraSans`, delete the Secret and upgrade so a new certificate carrying the new name is issued:

```bash
kubectl -n <namespace> delete secret <release>-sql-tls
helm upgrade <release> …
```

In Docker with `SQL_GATEWAY_TLS_ENABLED=true`, remove `/var/lib/classifyre/sql-tls` and restart the container to regenerate the CA and certificate for a new `SQL_GATEWAY_PUBLIC_HOST`.

### Check that it works

When TLS is enabled, the handshake from a machine outside the cluster (or the Docker host) confirms that the path is open and the certificate carries the name you set:

```bash
echo | openssl s_client -connect sql.example.com:5432 -tls1_3 -alpn postgresql 2>/dev/null | grep -E "Protocol|subject"
# Protocol: TLSv1.3
# subject=CN=sql.example.com
```

When TLS is disabled, test directly with `psql` using `sslmode=disable` (e.g. `psql "host=localhost port=5433 dbname=default user=<user> sslmode=disable"`).

Then reload the app: the warning is gone and **Connect a tool** shows the host and port. Troubleshooting:

- **The warning stays**: `publicHost` is empty. Check the API pod: `kubectl exec deploy/classifyre-api -- printenv SQL_GATEWAY_PUBLIC_HOST`.
- **Connection refused or a timeout**: the port is not exposed. Check the Service type, the node's or cloud firewall and `allowedCidrs`.
- **A certificate error with `verify-full`**: the name you connect to is not the one on the certificate. After changing `publicHost`, delete the kept certificate so the chart makes it again (`kubectl -n <namespace> delete secret <release>-sql-tls`, then `helm upgrade`; the gateway restarts) and download the new CA.
- **Sessions refused as busy**: the gateway pod is out of memory for another session; see `maxSessions` and the pod's memory limit below.

### Turning it off, and what it costs

If you do not want SQL connections, set `sqlGateway.enabled: false`: no pod, no Service, and the app says they are switched off. With it on, the gateway pod requests 100m CPU and 256 MiB (limit 1 GiB) plus its `catalog-postgres` sidecar; on a small or shared node adjust `sqlGateway.resources`.

When TLS is enabled, connections use TLS 1.3 only. Other settings: `maxSessions` per gateway pod, `maxSessionsPerConnection`, `idleMinutes`. Ten failed sign-ins within 15 minutes lock a user name, and an address, out for 15 minutes.

## Preventing direct database bypass in production

Classifyre enforces row filters, column masking, and audit logging on every query that passes through its SQL workbench, SQL gateway, and MCP server. Because Classifyre does not replace your underlying databases, production deployments enforce non-bypass operationally in two steps:

1. **Revoke direct analyst and shared BI credentials on the source systems.** Analysts, BI dashboards, and AI agents authenticate only with personal, expiring Classifyre SQL connections or MCP tokens — never with raw database accounts.
2. **Restrict source network reachability to Classifyre's service principal.** Use firewall rules, VPC security groups, or Kubernetes `NetworkPolicy` so source database ports (e.g., PostgreSQL `5432`, SQL Server `1433`, Oracle `1521`) accept analytical traffic exclusively from Classifyre's dedicated query workers and application backends — never from analyst laptops, BI desktops, or AI agent hosts.

With those two controls in place, Power BI, Excel, Tableau, DBeaver, ODBC clients, and MCP AI agents have no alternative path to raw tables: every analytical read is governed, masked, and logged by Classifyre.
