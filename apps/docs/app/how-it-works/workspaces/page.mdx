# Workspaces

A **workspace** is a self-contained Classifyre instance-within-an-instance. One
deployment can hold many of them: one per client, per region, per business
unit, or per sensitive matter that must never mix with the rest.

Isolation is not a filter applied to shared tables. Each workspace gets its own
**PostgreSQL schema**, and every query a workspace makes runs inside it. There
is no tenant column to forget, and no query path that can read another
workspace's rows.

> Workspaces are part of the open-source core and always on. They are also
> sometimes called *namespaces* — that is the term used in the API, the URL,
> and the database schema names.

---

## What each workspace owns

Nothing in this list is shared between workspaces:

| Owned outright | Notes |
| --- | --- |
| Database schema | A dedicated `ns_…` PostgreSQL schema, migrated independently |
| Sources & scans | Connections, schedules, and run history |
| Assets & findings | Everything a scan registers or a detector raises |
| Cases & inquiries | The whole investigation layer, including hypotheses and events |
| Custom detectors | Definitions, training examples, and test scenarios |
| Semantic space | Embeddings, importance ranking, and duplicate matching |
| Autopilot memory | Harness AI's memory, system brief, and glossary |
| Scan queue | Its own job queue, so one busy workspace cannot starve another |
| MCP endpoint | A distinct URL an MCP client connects to |
| Notifications | Its own feed and unread state |

Shared across the instance: the workspace registry itself (names, slugs,
thumbnails, categories, and links), the application version, and the machine or
cluster it all runs on.

## Addressing a workspace

Every workspace has a **slug** and an immutable **UUID**. The slug appears in
every URL, right after the host:

```
https://<your-host>/<workspace>/findings
https://<your-host>/<workspace>/sources/<source-id>
https://<your-host>/<workspace>/mcp
```

This is the same contract at every layer — the app, the REST API, the MCP
endpoint, WebSocket subscriptions, and the callbacks a running scan makes back
into the API. A request without a workspace segment is rejected; a request with
an unknown one returns `404 Unknown namespace '<value>'`.

Because the address carries the workspace, an integration is scoped by
construction: point an MCP client or an API token at `/<workspace>/…` and that
workspace is the only estate it can ever read.

The slug is **editable** — renaming a workspace changes its URLs but not its
data, because the underlying schema is derived from the UUID, not the name. A
handful of names are reserved (`api`, `namespaces`, `docs`, `health`, `ping`)
and cannot be used as slugs.

## Working with workspaces

**Choosing one.** Opening Classifyre lands you on the workspace directory: a
card per workspace with its name, description, links, and a live count of
sources and failing sources, **grouped by category**. Pick one to enter it; use
*All workspaces* in the sidebar to come back.

**Creating one.** *New workspace* asks for a name, its categories, and an
optional description and thumbnail. Classifyre derives a slug, creates the
schema, runs migrations into it, and starts its workers — usually a few
seconds. There is no default workspace: a fresh install has none until you
create the first.

**Renaming one.** Workspace settings let you edit the name, description,
thumbnail, categories, links, and URL slug at any time.

**Retiring one.** Deleting a workspace removes it from the directory and stops
its workers and scheduling, and any request to its URL then 404s. **The data is
retained** — the schema is never dropped — and the slug stays reserved so it
cannot be silently reused by a different investigation.

**Remote workspaces (desktop).** The desktop app can also list a workspace that
lives on another Classifyre instance. It appears in the directory alongside
local ones and opens that instance in your browser; no data is copied to your
machine.

## Categories

Ten workspaces are a list. Sixty are a filing problem. **Categories** are the
shelves the workspace directory is arranged on: *Clients*, *Internal*,
*Regulated*, *2026 matters* — whatever division your work actually has.

A category is deliberately shallow. It has a name and an optional description,
nothing more: no nesting, no rules, no effect on what a workspace can see or
do. It exists to make a long directory readable, and that is all it does.

### The rules worth knowing

- **Every workspace is in at least one category.** There is no uncategorised
  state to leave a workspace stranded in. Save a workspace with no category
  selected and Classifyre files it under **General**, the built-in default.
- **A workspace can be in several.** A client matter that is also under
  regulatory review is filed under both, and appears under both headings in the
  directory. Categories are labels, not folders — nothing moves.
- **General cannot be deleted.** It is the fallback every other rule leans on.
- **Deleting a category never deletes a workspace.** The label is removed; any
  workspace that is left with no label at all falls back to General.
- **Renaming one is felt everywhere** — the directory heading, the sidebar, and
  every card that carried it.

### Where categories show up

**The directory** groups its cards under category headings, in alphabetical
order, with a count beside each. A workspace filed under two categories appears
under both. When everything is in a single category the headings are hidden —
one heading over every card is a line to skip, not a structure.

**The sidebar**, inside a workspace, names the category directly under the
workspace name. It is a link: click it to see everything filed alongside what
you are working in. When a workspace sits in several, the first is shown with a
`+n` for the rest.

**The category page** lists every workspace on that shelf, as the same cards
the directory uses, and is where you rename or delete that category.

**The category index** (*Categories*, from the directory toolbar) is the map of
the whole filing system: every category in order, its description, the
workspaces on it by name, and a way into each one.

### Creating and assigning

Categories are picked from a dropdown when you create a workspace, and from the
same dropdown in workspace settings afterwards. If the shelf you want does not
exist yet, *New* creates it right there — without leaving the form — and
selects it for the workspace you are filling in.

<Callout type="info">
Upgrading an existing instance does not ask you to re-file anything. The
upgrade creates **General** and puts every workspace you already have into it,
so the directory looks exactly as it did before, with grouping ready when you
want it.
</Callout>

Categories are instance-wide, like the workspace registry itself: everyone
looking at the same Classifyre sees the same shelves. They are not an access
boundary — a category does not hide anything from anyone. Restricting *who may
open which workspace* is the governance question below.

## Links on a workspace card

A workspace usually has a life outside Classifyre: the case tracker, the
engagement folder, the client's own portal, the ticket that started it. Each
workspace can carry a list of **external links** — a name and a URL, both
required — shown on its card in the directory and opened in a new tab.

Add them in workspace settings, in the order you want them read. The name is
what appears on the card, so name them the way you would say them out loud
("Case tracker", not "https://tracker.example.com/b/1183"). Links must be
ordinary `http://` or `https://` addresses; up to twenty per workspace.

They are a signpost, not an integration: Classifyre stores the address and
nothing else. It does not fetch these pages, scan them, or know whether whoever
clicks can open them.

## Upgrades and migrations

Every workspace schema is migrated on every start. When Classifyre boots, it
reads the registry and applies any pending database migrations to each
workspace in turn, under a lock shared across all API and worker processes, so
a multi-replica cluster never migrates the same schema twice. Adding a
workspace later migrates it at creation time.

The practical consequence: upgrading Classifyre upgrades every workspace. There
is no per-workspace upgrade step and no way for one workspace to drift onto an
older schema version.

## Deleting a workspace

Deleting a workspace is a two-stage operation, and only the first stage is
reversible.

Deleting it immediately stops it being served: it disappears from the
directory, its URL returns 404, and its scans, schedules and background workers
are torn down. Its data is untouched — the workspace's database schema and
everything in it survive, and its slug stays reserved so it cannot be quietly
reused by a new workspace.

**Seven days later, a background sweep drops that schema for good.** At that
point the workspace, its assets, its findings and its investigations are gone,
and Classifyre has no way to bring them back. There is no automatic backup
taken before the drop — if you need one, take it during the grace period.

The window exists because a workspace deleted by mistake is worth recovering,
and a workspace deleted on purpose should not keep its disk forever. On one
instance, eleven deleted workspaces were still holding 11.8 GB of a 64 GB
database.

On Kubernetes, `api.namespaceRetentionDays` changes the window; setting it to
`0` disables the sweep entirely and keeps deleted workspaces indefinitely.
Recovering a workspace inside the window is a database operation rather than a
button — get in touch if you need to do it.

<Callout type="warning">
Workspace schemas that have no registry entry at all — left behind by much
older versions — are deliberately **not** swept, because there is nothing to
confirm what they were. Those need a deliberate manual cleanup.
</Callout>

## Governance and access control

The open-source core gives you **isolation** — the walls between workspaces.
What it deliberately does not ship is **authorization**: it has no built-in
concept of users, roles, or who may open which workspace. Anyone who can reach
the instance can switch between the workspaces on it.

That is fine for a single investigator on the desktop app, or for a deployment
that is already behind your own access layer. If you need governed workspaces —
SSO, roles, and per-workspace authorization so an auditor sees only the audit
workspace and a regional team only its region — that is part of the enterprise
offering. See [Deployment](/deployment/) or get in touch at
`contact@classifyre.com`.
